# Save Generated Images to Compatible Object Storage (With Private Access Until Deletion)

A generated image that belongs to a signed property document should go into private object storage as bytes, with its deletion deadline recorded in application data. Deliver it through a short-lived authorized path; use a backend proxy only when response-level control matters more than operational simplicity.

| Choice | Access-control boundary | Delivery work | Best fit |
| --- | --- | --- | --- |
| Short-lived signed object URL | Application authorizes issuance; storage validates the signed request | Low after issuance | Routine tenant downloads |
| Authenticated backend proxy | Application checks every request and streams every byte | Higher | Strict download headers, immediate revocation, or audit at delivery time |

**Recommendation:** keep the bucket private, upload the image `Buffer` with an explicit media type, and start with short-lived signed delivery. Keep the deletion deadline in the database, not only in an object key or a storage lifecycle rule. That split is dull on purpose. It lets one person ship weekly without making the application server a permanent image pipe.

## How should Node.js save a generated image buffer to compatible storage?

The useful question is not whether an object is private. It is: where does authorization happen for each read?

With signed delivery, the application authenticates the property manager, checks that the lease belongs to the manager's organization, and then issues a URL that expires. The object store handles the byte transfer. Treat that URL as a bearer credential: keep its lifetime short, avoid logging its query string, and never persist it as the document's durable location. Persist the object key instead.

Consider one lease record with a 10-minute download URL and a deletion deadline 90 days away. Revoking that URL does not touch the retained PNG; deleting the PNG does not invalidate a copy already downloaded by an authorized manager. The application therefore checks the organization before issuing each URL, stores the absolute deletion time beside the lease record, and lets a separate worker enforce that deadline. Mixing those jobs into one `expiresAt` field looks convenient, but it leaves the operator unable to tell whether the timestamp governs a credential or the evidence itself.

A proxy keeps the application in the read path. That makes it easier to reject a request after a user's access changes and to set `Content-Disposition` for a controlled download filename. MDN documents both the `inline` and `attachment` dispositions and the `filename` parameters. The trade is direct: every download now consumes application connections, bandwidth, and failure budget. For a one-person SaaS, that is undifferentiated work unless the control is genuinely required.

Access checks must use server-owned identity. Do not accept an organization ID from a query parameter and interpolate it into a key. Load the document by its opaque ID, verify membership, then read the stored key. One missed comparison turns a neat storage abstraction into cross-tenant disclosure.

## Put the deletion deadline beside the business record

A signed lease attachment has two clocks. The download credential may expire in minutes, while the retained object may have an explicit deletion date set by policy or contract. Those clocks solve different problems. URL expiry limits access to one issued credential; it does not delete the object.

I optimize this decision for revenue per engineering hour: the database owns `deleteAfter`, a scheduled worker selects due records, and object storage holds the bytes. The worker should delete by the exact stored key and mark completion only after the storage operation succeeds. Retry failures with bounded backoff, and alert on the age of the oldest overdue record. A daily count alone can hide one object that has been stuck for weeks.

Lifecycle policies can provide a useful backstop when their age rules match the requirement, but they should not be the only record of a document-specific deadline. Calendar dates, legal holds, and tenant-specific retention changes belong in application state. Make deletion idempotent as well: an absent object can be treated as the desired end state after the application confirms it is addressing the right key.

This is the core constraint.

## Upload once, retain the evidence

The storage adapter below stays vendor-neutral. It accepts the generated bytes rather than a public URL, creates an unguessable key, and records enough information for later delivery and deletion. The concrete client can target any compatible object service whose behavior you have tested.

```ts
import { randomUUID } from "node:crypto";

type ObjectWriter = {
  put(input: {
    bucket: string;
    key: string;
    body: Buffer;
    contentType: "image/png";
    metadata: Record<string, string>;
  }): Promise<{ etag?: string }>;
};

type RetainedImage = {
  id: string;
  organizationId: string;
  objectKey: string;
  contentType: "image/png";
  byteLength: number;
  deleteAfter: Date;
  etag?: string;
};

export async function retainLeaseImage(input: {
  storage: ObjectWriter;
  bucket: string;
  organizationId: string;
  leaseId: string;
  png: Buffer;
  deleteAfter: Date;
}): Promise<RetainedImage> {
  if (input.png.length === 0) throw new Error("Generated image is empty");
  if (input.deleteAfter.getTime() <= Date.now()) {
    throw new Error("Deletion deadline must be in the future");
  }

  const id = randomUUID();
  const objectKey = `organizations/${input.organizationId}/leases/${input.leaseId}/${id}.png`;
  const result = await input.storage.put({
    bucket: input.bucket,
    key: objectKey,
    body: input.png,
    contentType: "image/png",
    metadata: { documentId: id },
  });

  return {
    id,
    organizationId: input.organizationId,
    objectKey,
    contentType: "image/png",
    byteLength: input.png.length,
    deleteAfter: input.deleteAfter,
    etag: result.etag,
  };
}
```

The database write and object upload are not one transaction. Plan for the gap. A practical sequence is to create a `pending` record first, upload, then mark it `ready`; a reconciliation job can remove abandoned objects and retry incomplete records. Do not expose a record until it is ready. Also verify the decoded media type and enforce a byte limit before upload. File extensions and upstream labels are inputs, not proof.

Test the adapter against the same compatible endpoint used in deployment. Cover an empty buffer, an interrupted upload, a duplicate job, a missing object during deletion, and an authorization attempt from another organization. The happy path is the cheap test.

## When is the proxy the better runner-up?

Choose the authenticated proxy when the application must decide on every download, when access must disappear immediately after a role change, or when the response needs a controlled `Content-Disposition` filename. It is also the clearer boundary when policy forbids bearer URLs, even short-lived ones.

But measure what you adopt. Track time to first byte, completed and aborted streams, upstream storage errors, and concurrent downloads. Stream the response; do not read the whole stored image into a second in-memory buffer. A proxy that buffers every download can turn a traffic spike into memory pressure with no product benefit.

Signed delivery remains simpler for routine access because the application leaves the data path after authorization. The decision can differ by document class. A normal inspection image may use signed delivery, while a signed lease packet may go through the proxy for attachment headers and per-request audit. One bucket does not require one delivery policy.

The limitation is clear: signed delivery is not suitable when policy requires the application to approve every byte transfer. The proxy's trade-off is equally plain. It buys immediate application-level control by putting bandwidth, connection lifetime, and storage failures back on the application server.

Choose deliberately.

## Operate the deadline, not just the upload

The upload is done when the object and ready record agree. The retention feature is done only when overdue objects are gone and that outcome is observable. Keep a metric for overdue ready records, log deletion attempts with the document ID and object key but no signed URL, and page on sustained age rather than a single retry.

Run a restore-style drill for metadata too. Losing the database mapping while retaining opaque objects makes authorization and deletion hard to prove. Conversely, deleting the row before the object makes the bytes easy to orphan. Backups need a retention policy that is explicit about when deleted document content ceases to be recoverable; do not imply that deleting the live object instantly erases every backup copy.

For a solo operator, the rule is compact: outsource byte durability and transfer, keep authorization and deadlines in the product, and automate reconciliation between them. Price can break a tie after access control, deletion semantics, compatibility tests, and operational effort are understood. It should not lead the design.
